스마트팜코리아의 Open API로 실제 온실 데이터를 모아, 시간을 압축해 다시 흘려보내는 "가상 온실"을 만들려고 한다. 코드를 쓰기 전에 기술명세서부터 Claude와 함께 읽었다. 이 글은 명세서에서 무엇을 읽었고, 그 결과 수집 방식을 어떻게 정했는지에 대한 기록이다.

아직 설계 단계다. 서비스키로 실제 호출을 해 보기 전에 쓴 글이라, 호출로 확인해야 할 항목은 맨 아래에 따로 모았다.

## 명세서에 서비스가 두 개 있다

내려받은 압축 파일에는 한글(hwp) 문서가 두 개 들어 있었다. 이름은 비슷하지만 서로 다른 서비스다.

| | 빅데이터 제공 서비스 | 작기별 빅데이터 제공 서비스 |
| --- | --- | --- |
| 주소 | `.../ProvideRestService/...` | `.../CropseasonRestService/...` |
| 조회 기준 | 농가(userId), 시설 + 날짜 | 작기(croppingSerlNo) |
| 환경 정보 | 시설과 날짜를 지정해 하루치 | 작기 전체를 1,000건씩 페이지로 |
| 생육 정보 | 딸기, 국화, 참외, 그 외로 오퍼레이션 4개. 컬럼이 제각각 | 오퍼레이션 1개. 항목코드 + 값 형태 |
| 작기 목록 | 농가 ID로 조회 | 연도로 조회. 환경·제어·생육 등록 여부 포함 |

둘 다 REST(GET)에 JSON이고, 요청값은 전부 URL 경로에 순서대로 넣는다.

```
GET .../CropseasonRestService/getCroppingSeasonEnvDataList/{서비스키}/{작기번호}/{페이지}
```

여기서 "작기"는 한 작물을 심어서 거둘 때까지의 한 주기를 말한다. 명세서 예시에는 2021년 1월 12일에 시작해 6월 30일에 끝난 토마토 작기가 나온다.

## 작기별 서비스를 고른 이유

내가 만들려는 것은 "작기 하나를 처음부터 끝까지 재생하는 것"이다. 그러면 필요한 데이터 단위도 작기다. 여기에 더해 세 가지를 따졌다.

**호출 수가 훨씬 적다.** 명세서 예시 작기는 환경 28,302건, 제어 19,747건이다. 작기별 서비스로는 1,000건씩 약 50번 호출하면 끝난다. 시설 + 날짜 방식으로 받으면 170일치를 환경과 제어 각각 불러야 하니 340번이다. 호출 한도가 명세서에 적혀 있지 않아서, 적게 부르는 쪽이 안전하다.

**받기 전에 쓸 만한 작기인지 알 수 있다.** 작기 목록 응답에 환경정보·제어정보·생육정보 등록 여부가 Y/N으로 들어 있다. 셋 다 Y인 작기만 골라 받으면, 받아 놓고 보니 비어 있는 경우를 피할 수 있다.

**생육 데이터를 테이블 하나로 받을 수 있다.** 다른 서비스는 딸기용 응답에는 화방수와 착과수가, 국화용 응답에는 초장과 줄기 직경이 컬럼으로 박혀 있다. 품목마다 DTO와 테이블이 따로 필요하다. 작기별 서비스는 "조사 항목 코드, 항목명, 값, 단위"가 한 줄씩 오기 때문에 품목이 달라도 같은 구조로 받는다.

다만 기준온도나 재배면적 같은 작기 상세값은 다른 서비스의 작기 정보에만 있다. 나중에 이상 감지 규칙을 만들 때 그 오퍼레이션 하나만 보조로 쓸 생각이다.

## 응답에서 조심할 것

명세서의 예제 응답을 보면서 구현할 때 실수하기 쉬운 부분을 적어 뒀다.

**상태코드는 배열의 첫 번째 원소에만 있다.** 응답은 배열이고, `statusCode`와 `statusMessage`는 0번 원소에만 값이 있다. 나머지는 null이다. 모든 원소에서 상태코드를 확인하는 코드를 짜면 두 번째 행부터 전부 실패로 처리된다.

```json
[
  { "statusCode": "00", "statusMessage": "NORMAL_CODE", "fatrCode": "CI", "senVal": "664.73" },
  { "statusCode": null, "statusMessage": null, "fatrCode": "TI", "senVal": "21.00" }
]
```

**숫자가 문자열로 온다.** 측정값(`senVal`), 수집 건수, 현재 페이지, 전체 페이지가 모두 문자열이다. 숫자 변환이 실패하는 경우를 처리해야 한다.

**항목코드는 분류코드와 같이 봐야 한다.** 측정 항목은 분류코드(내부환경 EI, 외부환경 EO, 토양 EL, 양액 NT, 제어 CR)와 항목코드의 조합이다. 그런데 항목코드 `DT`(이슬점온도)는 EI에도 있고 EO에도 있다. `WS`(풍속)도 마찬가지다. 항목코드만으로 "어떤 측정값인지" 판단하면 내부 값과 외부 값이 섞인다.

**전체 페이지 수를 믿지 않는다.** 명세서 예시에 전체 28,302건인데 전체 페이지가 28로 적혀 있다. 1,000건씩이면 29페이지여야 한다. 예시의 오타일 수도 있지만, 28페이지에서 멈추면 마지막 302건을 놓친다. 그래서 반복 횟수를 `totalPage`로 정하지 않고, 1,000건 미만이 올 때까지 다음 페이지를 요청하기로 했다.

**서비스키가 URL에 들어간다.** 주소가 http이고 키가 경로의 일부다. 요청 URL을 로그에 그대로 남기면 키가 로그 파일에 쌓인다. 로그를 찍을 때 키 자리를 가려야 한다.

## 명세서와 안내 페이지가 서로 다르다

API를 신청한 웹사이트의 안내 페이지와 명세서의 내용이 몇 군데 다르다. 명세서 파일은 2023년 9월에 만들어진 것이라, 그 뒤에 서비스가 바뀌었을 가능성이 있다.

| 항목 | 명세서 | 웹 안내 페이지 |
| --- | --- | --- |
| 작기 목록 요청값 | 연도 필수 | 서비스키만 |
| 시설 ID 필드명 | facilityId | fcltyId |
| 생육 조사일 형식 | yyyymmdd | yyyy-mm-dd |
| 선택 요청값 위치 | 전부 경로 | 쿼리스트링 |

어느 쪽이 맞는지는 문서를 더 읽어서는 알 수 없다. 두 형식을 모두 받을 수 있게 만들고, 실제 호출로 확인하는 수밖에 없다.

## 첫 호출로 확인할 것

- 작기별 서비스 주소로 2021년 작기 목록이 내려오는가
- 시설 ID 필드명이 어느 쪽인가
- 오류일 때 응답이 원소 1개짜리 배열인가, 다른 형태인가
- 마지막 페이지 다음을 요청하면 "데이터 없음" 코드가 오는가, 빈 배열이 오는가
- 환경 측정값의 시각 간격이 1시간인가
- 하루 호출 한도가 있는가

명세서를 읽는 데 든 시간에 비해 얻은 것이 많았다. 호출 수를 340번에서 50번으로 줄이는 결정과, 구현하다가 한참 헤맸을 함정 다섯 개를 코드 한 줄 쓰기 전에 찾았다. 다음 글에서는 이 데이터를 담을 테이블을 설계한다.
