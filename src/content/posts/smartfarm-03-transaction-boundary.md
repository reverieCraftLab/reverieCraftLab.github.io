[2편](/posts/smartfarm-02-table-design/)에서 만든 테이블에 데이터를 채울 차례다. 작기 하나를 받으려면 API를 약 50번 호출해야 한다. 그 사이에 네트워크가 끊길 수도 있고, 서버가 재시작될 수도 있고, API가 요청 제한을 걸 수도 있다.

목표는 하나다. 어느 시점에 죽어도 처음부터 다시 받지 않고, 끝난 곳 다음부터 이어서 받는다.

## 세 가지를 하나로 묶는다

페이지 1개 = 작업 1건 = 트랜잭션 1개로 정했다.

수집할 페이지마다 `collect_job` 테이블에 행을 하나 만든다. (작기, 종류, 페이지 번호)에 유니크 제약이 있어서 같은 페이지의 작업이 두 건 생기지 않는다. 상태는 PENDING, RUNNING, DONE, EMPTY, FAILED 중 하나다.

작업 하나는 세 구간을 거친다.

1. 작업을 선점한다
2. API를 호출하고 응답을 객체로 바꾼다
3. 저장한다

각 구간에서 트랜잭션을 어떻게 다루는지가 이 글의 내용이다.

## 1구간, 선점은 update 한 문장으로

스케줄러가 돌고 있는데 내가 수동으로 수집을 실행하면, 같은 작업을 두 곳에서 동시에 집을 수 있다.

```sql
update collect_job
   set status = 'RUNNING', attempt = attempt + 1, updated_at = now()
 where id = ? and status in ('PENDING', 'FAILED');
```

이 문장을 실행하고 "반영된 행 수"가 1이면 진행하고, 0이면 물러난다.

가장 먼저 떠오르는 방식은 `select`로 상태를 읽고, PENDING이면 `update`하는 것이다. 그 방식은 두 실행이 거의 동시에 `select`를 하면 둘 다 PENDING을 보고 둘 다 진행한다. 읽기와 쓰기 사이에 틈이 있기 때문이다.

update 한 문장에는 그 틈이 없다. DB는 같은 행에 대한 update를 한 번에 하나씩 처리한다. 먼저 온 쪽이 RUNNING으로 바꾸면, 뒤에 온 쪽은 `where` 조건에 맞는 행이 없어서 0건이 반영된다. 락을 따로 잡거나 버전 컬럼을 둘 필요가 없다.

## 2구간, API 호출은 트랜잭션 밖에서

실수하기 쉬운 곳이 여기다. 메서드 전체에 `@Transactional`을 붙이고 그 안에서 외부 API를 호출하는 것이다.

트랜잭션이 열려 있는 동안에는 DB 커넥션 하나를 계속 쥐고 있다. 외부 API 응답이 30초 걸리면 커넥션도 30초 동안 아무 일도 안 하면서 묶여 있다. 내 서버의 커넥션 풀은 5개로 잡을 예정이다. 수집이 커넥션을 붙들고 있으면 화면 쪽 조회 요청이 커넥션을 못 받아 멈춘다.

그래서 응답을 받고, 파싱하고, 검증까지 끝낸 다음에 트랜잭션을 연다. 트랜잭션 안에서는 DB 작업만 한다.

## 3구간, 데이터와 진행 기록을 같은 트랜잭션에

저장 트랜잭션 하나에 네 가지를 넣는다.

- 측정값 1,000건 배치 insert (`on conflict do nothing`)
- 생육 데이터면 조사항목 코드 upsert
- 현재 작업을 DONE으로 바꾸고 저장 건수 기록
- 다음 페이지 작업을 PENDING으로 insert

핵심은 뒤의 두 줄이다. 데이터 저장과 "여기까지 했다"는 기록을 따로 커밋하면 두 가지 어긋난 상태가 생길 수 있다.

| 먼저 커밋한 것 | 그 직후 죽으면 | 결과 |
| --- | --- | --- |
| 데이터 | 작업이 RUNNING으로 남음 | 다시 받는다. 중복은 PK가 걸러 주니 괜찮다 |
| 진행 기록 | 작업은 DONE인데 데이터가 없음 | 1,000건이 빠진 채로 아무도 모른다 |

두 번째가 무섭다. 오류도 안 나고 로그도 안 남는데 데이터에 구멍이 난다. 같은 트랜잭션에 넣으면 둘 다 반영되거나 둘 다 안 되거나 둘 중 하나라서, 이런 상태가 아예 생기지 않는다.

다음 페이지 작업을 여기서 만드는 것도 같은 이유다. N페이지가 DONE이 되는 순간 N+1페이지 작업이 반드시 존재한다. 사슬이 중간에 끊기지 않는다.

## 왜 작기 전체를 한 트랜잭션으로 묶지 않나

작기 하나가 "전부 들어가거나 하나도 안 들어가거나"면 더 깔끔해 보인다. 하지만 29페이지 중 28번째에서 실패하면 27페이지 분량의 호출을 버리고 처음부터 다시 받아야 한다. 호출 한도가 있는 외부 API를 상대로는 비싼 선택이다. 트랜잭션이 길어지면 커넥션을 오래 쥐는 문제도 다시 생긴다.

페이지 단위면 실패한 1페이지만 다시 받는다. 대신 "작기가 반쯤 들어간 상태"가 존재한다. 이건 작업 테이블을 보면 알 수 있으니, 화면에는 모든 작업이 끝난 작기만 보여 주면 된다.

## 다시 실행해도 안전하게

이 설계가 성립하려면 같은 페이지를 두 번 저장해도 결과가 같아야 한다. 2편에서 PK를 (작기, 시각, 분류, 항목)으로 잡고 `on conflict do nothing`을 쓰기로 한 것이 여기서 쓰인다.

이 성질 덕분에 복구가 단순해진다.

**실패 기록은 별도 트랜잭션으로 쓴다.** 저장 중 예외가 나면 그 트랜잭션은 롤백된다. FAILED 상태와 오류 메시지를 같은 트랜잭션에서 썼다면 그것도 함께 롤백돼서 남지 않는다. 롤백이 끝난 뒤 새 트랜잭션으로 기록한다.

**멈춘 RUNNING을 되돌린다.** 프로세스가 죽으면 RUNNING 상태의 작업이 남는다. 서버를 켤 때 10분 넘게 RUNNING인 작업을 PENDING으로 바꾼다. 실제로는 저장까지 끝났는데 상태만 못 바꾼 경우라도, 다시 받아서 넣으면 중복이 걸러지니 문제없다.

애매하면 다시 돌리면 된다는 것이 이 구조의 가장 큰 장점이다.

## Spring에서 걸리는 지점

**@Transactional은 같은 클래스 안에서 호출하면 적용되지 않는다.** Spring은 빈을 프록시로 감싸서, 바깥에서 메서드를 부를 때 트랜잭션을 연다. 같은 클래스 안에서 `this.save()`로 부르면 프록시를 거치지 않아 트랜잭션이 열리지 않는다. 오류도 나지 않아서 알아채기 어렵다.

그래서 클래스를 둘로 나눈다.

```java
@Component
class CollectRunner {            // 트랜잭션 없음
    void run(long jobId) {
        if (!jobs.claim(jobId)) return;          // 1구간
        Page page = client.fetch(...);           // 2구간, 트랜잭션 밖
        try {
            writer.save(jobId, page);            // 3구간
        } catch (Exception e) {
            jobs.markFailed(jobId, e);           // 별도 트랜잭션
        }
    }
}

@Component
class PageWriter {
    @Transactional
    void save(long jobId, Page page) { ... }     // 저장 + DONE + 다음 작업
}
```

**대량 insert는 saveAll이 아니라 JdbcTemplate으로 한다.** JPA로 ID를 직접 정한 엔티티를 저장하면, 새 행인지 기존 행인지 알기 위해 먼저 select를 한다. 1,000건이면 select가 1,000번이다. 그리고 `on conflict`는 JPA로 표현할 방법이 없다. `JdbcTemplate.batchUpdate`로 SQL을 직접 쓴다.

**JDBC URL에 reWriteBatchedInserts=true를 붙인다.** 이 옵션이 있으면 PostgreSQL 드라이버가 insert 1,000개를 여러 행짜리 insert 몇 개로 합쳐서 보낸다. 없으면 문장이 하나씩 전송된다.

## 결과코드에 따라 다르게 대응한다

API의 결과코드는 17가지다. 전부 "실패"로 뭉뚱그리면 재시도해야 할 것과 하면 안 되는 것이 섞인다.

| 코드 | 의미 | 처리 |
| --- | --- | --- |
| 00 | 정상 | 저장 |
| 03 | 데이터 없음 | EMPTY로 기록하고 끝. 실패가 아니다 |
| 01, 02, 04, 05, 99 | 서버 쪽 일시 오류 | 간격을 늘려 가며 최대 3회 재시도 |
| 22 | 요청 제한 초과 | 이번 실행을 멈추고 다음 스케줄에 이어서 |
| 10, 11, 12 | 요청 형식 오류 | 재시도하지 않는다. 내 코드나 명세 변경을 확인 |
| 20, 21, 30~33 | 키, 권한, IP 문제 | 수집 전체를 멈춘다 |

특히 22번에서 바로 재시도하면 제한에 계속 걸린다. 작업 상태가 DB에 남아 있으니, 그냥 멈췄다가 다음 날 이어서 받으면 된다. 페이지 단위로 진행 기록을 남긴 덕을 여기서도 본다.

## 테스트로 확인할 것

구현하면 다음 두 가지를 실제 PostgreSQL(Testcontainers)로 검증할 생각이다. H2는 `on conflict` 문법이 달라서 쓸 수 없다.

- 같은 페이지를 두 번 저장해도 행 수가 같다
- 저장 중 예외를 일으키면 측정값도, 작업 상태도, 다음 페이지 작업도 전부 반영되지 않는다

그리고 수집 도중에 프로세스를 강제로 죽였다가 다시 켠 뒤, 최종 행 수가 API가 알려 준 전체 건수와 같은지 본다. 이게 통과하면 이 글의 설계가 맞았다는 뜻이다.
